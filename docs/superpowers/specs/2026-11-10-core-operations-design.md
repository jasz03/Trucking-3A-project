# Core operations design

## Intent

Build the first usable slice of a Philippine trucking management system: an office dashboard and driver mobile app sharing actual records. The source brief is `C:/Users/Jasper/.codex/attachments/a2574673-bc25-43cf-8ac4-925261252d1d/Pasted text.txt`.

## Scope

1. Authentication and server-enforced roles. An owner invites users; a driver sees only their own assignments, tracking session, and attendance.
2. Truck and driver records with availability and license expiry.
3. Trip creation, assignment, and a guarded status lifecycle. One active trip per truck and driver.
4. Explicit driver-controlled tracking during an assigned trip. Every location has a captured time and server receipt time; stale points are shown as last known, never live.
5. Photo attendance with GPS accuracy, server receipt time, private photo storage, and HR review.

The later phases are payroll, quotations, accounting, maintenance, and reporting. Their data can connect to the first slice through stable IDs; they are not represented as working controls yet.

## Approaches

- **Next.js with a separate API and Postgres:** flexible, but requires two deployable backends and more free-tier operations.
- **Static React dashboard + Expo + Supabase (chosen):** one Postgres/Auth/Storage backend; RLS and database functions enforce access and assignment rules. The static dashboard deploys to Cloudflare Pages. The cost is tighter coupling to Supabase, isolated behind small application data modules.

## Data and access

Supabase Auth holds credentials. A `profiles` table holds approved role and display name; only an owner can change roles. The first owner is bootstrapped with SQL. An Edge Function lets an owner or administrator invite users without exposing the service-role key. Tables: drivers, vehicles, trips, trip_events, tracking_sessions, location_points, attendance. All are protected by RLS. Sensitive writes use `security definer` database functions that recheck the caller role and assignment; functions have a fixed search path. Attendance photos live in a private bucket, read only by the employee and HR/owner/administrator.

## Experience

The office dashboard uses a dark ink sidebar, warm off-white canvas, restrained amber highlights, clear data tables, and a location list/map pane. Empty states explain what to create next. The driver app is task focused: assigned trip, explicit Start/Stop sharing, status update, and attendance capture.

## Tracking and attendance truth

The app requests foreground/background permission before starting location updates. Background tracking requires a development or production build; Expo Go is insufficient. Tracking stops at trip completion or when the driver taps Stop. The database accepts points only for a caller's active session and assigned trip. Offline points keep their device capture time and are labeled delayed on upload. Device coordinates and photo are evidence submitted by the user, not independently verified presence. Attendance receipt time is generated by the database. No facial recognition.

## Test deployment

Cloudflare Pages hosts the static dashboard; Supabase Free hosts Auth, Postgres, Realtime, and private photo storage; Expo EAS Free builds the driver test app. A configurable map provider key is optional for the first rollout. No real employee data should be loaded before privacy notice, retention period, backup plan, and access review are agreed.

## Limits and open integration work

No Supabase or map credentials were supplied, so the software can be built and checked locally but cannot be connected to a live project or deployed yet. Routing, reverse geocoding, offline attendance queue, hardware trackers, and geofencing follow as separate work after the core workflows are proven.
